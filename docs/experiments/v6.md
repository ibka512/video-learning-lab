# 对象属性验证 v6 实测报告

日期：2026-10-30。既有 Godot 开发样本，6组24个位置，28个对象范围任务、40个属性目标。

## 结论

已实现独立属性记录、原生单图与时序单帧对照，以及只追加证据的回看。原始观察不会再因补读一致而被覆盖；但模型仍不能可靠区分前景运行窗口和背景编辑器。没有达到自动知识入库条件。

原生单图与时序单帧都是 32/40。两组有 31 项同时正确、7 项同时错误，仅 2 项答案不同。原生单图未显示整体优势。

## 本轮实现

- 将前景窗口身份、演示内容、菜单第一项分成独立任务范围；内容以可见/未见/无法确定分别记录，可同时保存碎片、手部、蓝色圆形等属性。
- 每次最多回答两个属性，取消生成对象框、标题、自由描述和重复的置信度字段。
- 原生图像和重复单帧视频使用同一源裁切、文本任务、输出结构、模型和像素预算。
- 原始观察作为不可替换的记录；编码对照、补读观察按来源追加；分歧显式保留，重复一致不升级为已核准事实。
- 沿用已有外接盘环境与 Qwen3-VL-4B-Instruct-4bit。未新增依赖、权重或外部服务。

## 输入对照与修复

首次输入诊断只完成2次调用即被尺寸检查停止：时序路径为960×512，原生路径为1408×768，不能公平比较。原因是实际加载的 MLX numpy 图像处理器读取 min_pixels/max_pixels，而最初修改了另一个处理器惯用的 size 字段。两份诊断回执保留，排除在主成绩外。

修复为向实际调用显式传递像素预算，并增加真实处理器回归检查，覆盖普通裁切、菜单裁切、完整原图三种尺寸。正式运行前冻结修订协议；本轮没有改动旧版输入处理代码，也不能据这次新代码错误反推此前试验存在同样错误。

正式对照 28 对输入的缩放尺寸、媒体token数量及源裁切一致。更进一步，全部 28 对实际图像张量哈希相同。两条路径仍使用不同的图像/视频标记与相关位置处理，因此不是完全相同的语言模型输入，但本样本不支持仅切换标记路径就能解决窗口误认。

## 属性结果

| 指标 | 原生单图 | 时序单帧 |
|---|---:|---:|
| 全部属性正确 | 32/40 | 32/40 |
| 窗口身份正确 | 2/8 | 2/8 |
| 内容/勾选属性正确 | 30/32 | 30/32 |
| 可见内容召回 | 14/16 | 14/16 |
| 错报可见内容 | 0 | 0 |
| 漏报可见内容 | 2 | 2 |
| 不确定 | 0 | 0 |
| 两个共存属性都识别出来 | 2/4 | 3/4 |
| 一个位置所有属性均正确 | 16/24 | 16/24 |

本轮40项是新的独立属性目标，不与 v5 的24个主状态或18道选项题直接比较。窗口身份和内容分开后，能明确看到主要错误集中在身份归属，但“任务变小”与“属性定义改变”同时发生，不能把全部变化归因于其中一个。

多属性格式解决了存储上的互斥，不代表视觉注意力问题已经解决：F-3的手与碎片、C-3的圆形与碎片仍有漏项。模型也常把有独立运行标题栏的画面判成编辑器本体。

## 回看不覆盖的验证

本轮触发 2 个任务，完成 2 次补读，预算延期 0 个。28 条初始记录、40 个初始属性全部保留；最后有 2 个属性分歧，自动核准0项。

F-3：原生单图漏掉碎片，补读给出正确的可见候选；原始漏项与新增候选同时保留。M-3：原生单图正确读出勾选，补读却说未勾选；原始正确观察保持不变，冲突显式可见。这里“避免破坏”针对直接用补读结果覆盖初值，不把一次补读冒充旧版完整两轮策略。

另外，以 v5 C-2 保存的真实两轮补读回执复现旧覆盖路径，再通过 v6 的追加接口验证：原有正确碎片观察保留，两次错误完整背景观察成为冲突证据，不能投票替换初值。该工程回归不使用参考答案指导模型。

## 成本与验证

主运行 58 次调用：原生28、时序28、补读 2；格式失败 0。准备与生成累计 153.59 秒，模型加载 7.73 秒另计。另保留2次尺寸诊断，合计 60 份回执。

原生任务累计 72.48 秒，时序任务 74.82 秒，补读 6.29 秒。没有运行方差或完整人工复核计时，不能由这几秒差异声称原生路径普遍更快。

实际程序检查、原始记录保持、输入张量对应、旧交付未变及本地链接校验见 `交付校验.json`。测试数量不等于视频理解准确率。

## 尚未完成与下一步
