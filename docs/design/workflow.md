# B 站收藏视频学习流水线设计

版本：v2.0 · 2026-10-26  
状态：流程设计，待审阅；未安装依赖、下载模型或启动视频批处理。  
依据：前轮《视频全帧学习与时间轴转写方案》和《GitHub 视频学习项目借鉴调研》。本版收敛技术路线、阶段接口和验收条件。

## 1. 要交付的结果与已确定的选择

目标是把两个收藏夹中可访问视频的实际声画内容，转成 AI 能检索、理解和引用的知识库。每个 BV 一份主 Markdown，所有分 P 分别保留完整转写、时间轴、知识单元和覆盖报告，再按领域建立索引。

前轮快照为“创作·设计”185 条、“技术·工具”565 条，共 750 条收藏、739 个不同 BV。这个数字用于导入对账；实际执行前更新收藏快照、展开各 BV 的真实分 P。旧接口的 page 字段不能直接当作选中的分 P。

本版确定以下基线：

| 事项 | 采用的设计 |
|---|---|
| 输入范围 | 固定一次收藏快照；处理其中所有可访问 BV 的全部实际分 P；后续新增另建增量批次 |
| 观看标准 | 默认严格逐帧：所有源解码帧进入视觉模型输入，不自动改成抽样模式 |
| 转写来源 | 从该分 P 自己的音轨独立 ASR；平台字幕只作经校验的辅助对照 |
| 时间基准 | 保留原始 PTS 和 time_base，使用统一的分 P 播放时间轴 |
| 主工程 | 本地 Python 调度、SQLite 状态、压缩 JSONL 证据记录、Markdown 输出 |
| 语音首选 | 借鉴 VideoLingo，验证 MLX 上的 Qwen3-ASR 1.7B 与 ForcedAligner 0.6B，分阶段装卸 |
| 视觉首选 | 验证 MLX-VLM + Qwen3-VL-4B-Instruct 的兼容量化版本；具体 revision 在试运行时锁定 |
| OCR | 本地 Apple Vision；保留原字、位置与修订记录 |
| 本机并发 | 一次一个主要推理模型；一个分 P 优先走完闭环 |
| 知识输出 | 先写细粒度知识单元，再生成视频笔记和领域索引 |
| 质量控制 | 覆盖审计、逐事件遗漏复核、重点片段回看三者共同决定完成状态 |
| 既有笔记 | 保留前轮元数据预整理；声画验证后的知识库另存 v2 |

AI 的使用方式为：读取领域索引 → 检索知识单元 → 检查环境、条件与版本 → 引用步骤和原片证据。Markdown 提供持久知识，不会自动改变模型权重。

“所有帧已输入”和“所有知识都理解正确”分开验收。前者可以核对输入记录；后者需要原始证据复核和样本标注，不用模型自行打出的置信度代替准确率。

## 2. GitHub 项目怎样用到流程里

采用一个轻量主工程，按模块学习已有项目；不同时接入多个完整应用。

| 项目 | 具体采用 | 本版边界 |
|---|---|---|
| bili-sync | 收藏夹分页、来源校验、同步状态和去重的实现思路 | 导入后转成统一媒体清单；失败条目保留，不沿用“超过次数即丢弃”策略 |
| VideoLingo | MLX ASR/对齐路线、180 秒分块、异常短稿与循环检测、缓存身份 | 只取语音处理需要的能力；不引入翻译、配音和整个 Web 应用 |
| course2md | 画面与讲解时间轴、分段恢复、参数变化使缓存失效、文档组织 | 将这些设计落实在主工程；CLI 可用于对照验证，不作为第一版必需运行层 |
| BiliNote / VideoToNo | 时间跳转、证据图、长稿分段、转写与笔记生成之间的接口 | 输出层参考；本版先提供本地文件和命令入口，MCP 后续按需要接 |
| VideoRAG | 跨视频主题关联、来源片段回溯 | 知识库可靠后再借鉴检索结构；第一版使用 SQLite FTS |

VideoLingo 源码已经有 Apple Silicon 的 MLX ASR 和 MLX 强制对齐路径，两者分别加载；其实现可作为第一条待测路线。[语音后端](https://github.com/Huanshere/VideoLingo/blob/01f843492759be9bbfd1a5cb697b799cc9de1609/core/asr_backend/qwen_asr_local.py#L79-L92)、[MLX-Audio 官方说明](https://github.com/Blaizzy/mlx-audio#qwen3-asr--forcedaligner)

本版据此把上一方案的 whisper.cpp 调整为质量或运行问题出现时的对照后端。试运行通过后只保留一套默认 ASR，避免长期维护几套重复流程。替换后端时只重做相关阶段。

course2md 默认按秒采样，不能直接用作严格全帧分析器；本版借鉴其检查点和时间轴设计。[采样实现](https://github.com/mizorewww/course2md/blob/e46b7d552d402a9f7868dcbaee7686f80565f2bd/src/scene.rs#L72-L84)、[检查点设计](https://github.com/mizorewww/course2md/blob/e46b7d552d402a9f7868dcbaee7686f80565f2bd/src/checkpoint.rs#L1-L14)

## 3. 从收藏夹到知识库的完整流程

~~~mermaid
flowchart TD
    A[收藏夹快照] --> B[BV 去重与真实分 P 展开]
    B --> C[按需获取媒体并校验身份]
    C --> D[建立原始时间轴和媒体清单]
    D --> E[原音轨 ASR 与强制对齐]
    D --> F[顺序解码全部帧]
    F --> G[原分辨率 OCR 与连续帧视觉分析]
    D --> H[声音区间及非语音事件登记]
    E --> I[声画事件融合]
    G --> I
    H --> I
    I --> J[知识 技术 步骤 参数 经验]
    J --> K[逐事件遗漏复核和覆盖审计]
    K --> L[按视频输出 MD 与完整转写]
    L --> M[领域索引与检索]
    K --> N[问题队列与针对性重做]
    N --> E
    N --> G
    N --> J
~~~

图中分支表示数据关系。本机实际按资源顺序执行，不同时加载 ASR、对齐器和视觉模型。

| 阶段 | 输入 | 必须产出 | 进入下一阶段的条件 |
|---|---|---|---|
| 1. 收藏导入 | 两个收藏夹及前轮清单 | 批次快照、收藏来源映射、BV 清单 | 分页完整；条目总数可对账；重复项合并来源 |
| 2. 分 P 与媒体 | BV、当前可访问资源 | 分 P 清单、原媒体、来源与文件 hash | BV/aid/CID/分 P 无身份冲突，下载和解码探测成功 |
| 3. 时间轴 | 原始音视频流 | 逐帧索引、音轨映射、总时长与偏移 | 实际 PTS、音画偏移和播放跳转对应 |
| 4. 语音 | 原音轨及其时间映射 | 原稿、校订稿、词/字时间、VTT/SRT、问题清单 | 全音轨分区登记；语音区间有转写或明确未识别原因 |
| 5. 视觉 | 全部源帧 | OCR、视觉观察、帧输入回执、证据图 | 无跳帧、无静默截断；失败窗口已补做或显式阻塞 |
| 6. 事件融合 | 转写、视觉、声音事件 | 按时间组织的事件及声画冲突 | 每个源时间区间都能定位到事件；跨窗口动作衔接 |
| 7. 知识提取 | 事件和源证据 | 概念、步骤、参数、经验、限制等知识单元 | 每条事实和关键步骤可回溯，未展示内容标明未知 |
| 8. 复核 | 完整事件、原始观察、知识单元 | 遗漏补充、覆盖报告、问题状态 | 硬性完整性条件通过；严重问题处理完 |
| 9. 输出 | 通过检查的分 P 与知识单元 | 每 BV 主 MD、完整转写、领域索引 | 输出引用有效；所有实际分 P 的状态明确 |

收藏条目不能因为已生成 Markdown 就被标记为完成。一个 BV 只有在全部实际分 P 达到相应标准后，才获得完整完成状态。

## 4. 媒体清单和时间轴先做可靠

### 4.1 身份与去重

主键分为三层：

- 视频：BV，记录原始 aid 和全部来源收藏夹。
- 分 P：BV + CID；序号、标题和时长作为可变元数据。
- 媒体版本：分 P + 原文件 SHA-256；发生内容变化时新建版本，不覆盖旧证据。

分页导入保留收藏夹 ID、页面结果和抓取时间。前轮本地 BV 清单用于差异对账，不能让旧清单限制新快照发现的条目。

媒体获取时保存请求身份、返回元数据、实际流信息和完整文件 hash。BV/CID 一致是必要条件，还需检查时长及开头、中间、结尾的声画内容是否吻合。临时播放 URL 只用于获取，不写入可长期依赖的引用。凭据留在本机，日志不记录 Cookie 或访问令牌。

获取不到媒体的条目分别标记删除、访问受限、登录失效、网络错误或待核查。允许继续处理其他视频；这些条目仍在总清单和失败报告中。

bili-sync 的收藏夹分页和返回结果验证可作为导入器参考。[分页实现](https://github.com/amtoaer/bili-sync/blob/c900777e78796653fdfb00421879b6a802d1eedd/crates/bili_sync/src/bilibili/favorite_list.rs#L71-L103)

### 4.2 全流程共用时间基准

保留源 PTS 与有理数 time_base，再计算统一播放时间：

~~~text
part_time = source_pts × source_time_base − common_origin
~~~

common_origin 对整个分 P 一致；不能把音轨和视频各自从 0 开始后直接合并。保留容器起点、流偏移、重采样映射、分块起点和播放器跳转映射。

变帧率按实际显示时间戳排序；帧 ID 使用解码显示顺序编号，不用“帧号 ÷ 30”推算时间。相同 PTS 的多个帧仍有不同 ID。音频时间存在间断时，记录分段映射；生成静音填充也须登记，不能悄悄拉直音轨。

元数据给出的 nb_frames 或名义帧率仅作参考。顺序解码建立实际帧清单，配合 ffprobe 计数和解码错误日志核对；参考数量未知时显示未知，不显示 100%。[ffprobe 官方文档](https://ffmpeg.org/ffprobe.html)

第一版拟采用 PyAV 逐帧读取图像和 PTS，FFmpeg/ffprobe 负责媒体探测与音频转换。PyAV 是拟新增的运行依赖，其许可证为 BSD 三条款；具体版本、FFmpeg 构建与所需依赖在实施准备时固定。[PyAV 项目](https://github.com/PyAV-Org/PyAV)、[许可证](https://github.com/PyAV-Org/PyAV/blob/main/LICENSE.txt)

## 5. 语音转写和声音事件

处理顺序固定为：

1. 保留原音轨，建立全音轨区间清单；另生成 ASR 所需的单声道重采样副本。
2. 记录语音、音乐、静音、混合与不确定区间。检测结果用于调度，不据此永久删除音频。
3. ASR 默认以不超过 180 秒的块开始，尽量在低能量处切分；保存实际起止点，边界留重叠。
4. 使用 Qwen3-ASR 独立转写，保留原文；循环重复、异常短稿、语言突变和空输出触发检查。
5. 卸载 ASR 后加载 ForcedAligner，对原音频与确认的转写文本对齐，回填原片时间。
6. 按文本和时间共同处理重叠，不只凭相同句子删除正常重复讲解。
7. 结合清晰 OCR 提出术语、命令、数字和单位的校订；保留原稿、修订稿和理由。
8. 任何改变词序或内容的校订重新对齐；不能直接沿用旧词时间。
9. 生成句段转写 Markdown、VTT/SRT 和词/字符 JSONL；低可信词保留句段时间或标为未对齐。

180 秒是本流程采用的初始分块长度。官方 ForcedAligner 支持词或字符级时间，文档描述的最长音频范围为 5 分钟；实际仍需按固定运行版本和素材验证。[官方强制对齐说明](https://github.com/QwenLM/Qwen3-ASR#forcedaligner-usage)

ASR 的异常块先缩短到 60 秒重试；仍失败就保留问题。平台字幕只有身份和内容对应关系通过校验后才能参与对照，不能把来自其他 CID 或旧缓存的文字混入本视频。

非语音内容另存声音事件。对于音效、节奏、音色、发音或设备噪声教学，保存可回放音频范围和作者描述；没有经验证的听觉模型时，不能仅用响度变化写出声音含义。需要听辨而未完成的关键片段进入复核，不把它算作无知识。

## 6. 严格逐帧视觉处理

### 6.1 帧如何进入模型

顺序解码，保留每帧 ID、PTS、尺寸、像素校验值和处理状态。采用流式内存缓冲，只持久保存索引、观察结果和必要证据图。

初始窗口为连续 8 帧，窗口之间重叠 2 帧；这是试运行起点，最终按像素、上下文和内存测量调整。每个窗口携带：

- 有序帧 ID、真实时间与对应图像。
- 必要的原画面 OCR、局部高清裁剪。
- 上一窗口中仍在进行的动作与疑问。
- 本次需要记录的状态变化、操作、参数和结果。

第一轮视觉观察以画面证据为主；语音在事件融合时加入，降低模型用讲解文字代替观察画面的倾向。

8 帧在 30 FPS 视频中只覆盖约 0.27 秒，所以另建持续事件状态：跨窗口跟踪同一个操作、对象和参数；再按场景或约 10–30 秒合并观察。长动作不能被当成许多不相关小片段。

原分辨率 OCR 检查全部帧。完全相同像素的图像或区域可以复用已有 OCR，但逐帧记录复用依据；相似度高不能证明文字没变化。视觉语义输入在严格模式下仍包含这些帧。

### 6.2 防止“名义逐帧、实际抽样”

采用显式多图输入，控制可观测的本地处理器。逐请求登记：

~~~text
源帧集合 → 提交帧集合 → 预处理保留的源帧集合 → 实际模型输入 → 成功返回
~~~

需要验证预处理图像数、源帧到张量/视觉输入的映射、缩放和裁剪参数、输入长度及输出是否截断。模型内部的 patch 合并可以存在，但不能丢弃源帧；补齐用的重复帧单独标记，不作为新增覆盖。

输入回执由运行适配器记录，是对输入链路的证明；它不证明模型已经正确理解每个细节。只有完成有效推理、结构化输出校验成功的请求，才计入成功语义输入覆盖。一个请求失败时，该请求独有的帧不算成功；重叠重复帧按集合去重统计。

Qwen3-VL 的视频入口存在默认 2 FPS 等采样配置，因此本方案不直接把长视频路径交给默认处理器。MLX-VLM 的多图能力是候选输入路线，具体模型与处理器仍需实测。[Qwen3-VL 视频配置](https://github.com/QwenLM/Qwen3-VL#usage)、[MLX-VLM 多图说明](https://github.com/Blaizzy/mlx-vlm#multi-image-chat-support)

若具体运行后端不能提供足够的输入观测，就不能给出严格完成标记；可继续做开发诊断，不进入全量严格处理。

### 6.3 小字、代码和短暂画面

全图用于布局和动作，原分辨率局部用于代码、公式、按钮、数值和单帧短暂信息。每个裁剪必须绑定源帧和坐标。

代码保留原始 OCR、修订文本、语言与环境。模糊字符使用明确占位或疑问，不“补全成能运行的版本”。鼠标悬停不能直接写成点击；结果变化也不能证明具体快捷键。

缩小窗口、降低并发和增加裁剪是资源不足时的处理方式；不自动降低源帧覆盖率。

## 7. 从声画事件到 AI 知识

### 7.1 事件是知识整理的最小上下文

事件由主题、画面变化、操作过程、代码/参数变化和声音变化共同划分。长讲解按语义段切开，短操作保留完整前后状态。

每个事件记录时间范围、帧范围、转写引用、声音引用、观察事实、作者陈述、冲突和未展示部分。视频开头、结尾、静态讲义、无语音演示、广告和重复讲解都有事件记录；没有新增知识时填写具体原因。

知识与事件是多对多关系。同一知识可由多个不连续事件支持；同一事件也可能含多个步骤和经验。不能通过合并摘要丢掉中间的参数变化。

### 7.2 知识单元的写法

| 类型 | AI 使用前必须知道的内容 |
|---|---|
| 概念与原理 | 定义、因果关系、前提、例子、限制 |
| 技术与操作 | 目标、环境/版本、起始状态、输入、步骤、参数、成功现象 |
| 经验与取舍 | 场景、尝试、失败原因、调整、结果、适用边界 |
| 代码与公式 | 原片内容、变量/单位、依赖、使用位置、是否完整、是否实际验证 |
| 设计与作品分析 | 可观察效果、构成、顺序、作者解释、能否确定实现方法 |
| 工具评价 | 测试条件、作者立场、日期/版本、可复现程度 |

每条知识包含稳定 ID、领域与标签、简明结论、详细解释、时间段和证据引用。同一媒体版本内创建后保留 ID；拆分、合并或媒体内容变化时记录新旧关系，不能因重排章节就把旧 ID 指向另一条知识。结论及关键步骤分别标记依据：

- 画面直接展示。
- 作者明确陈述。
- 声音直接支持。
- 系统推断。
- 另行验证。

“作者说可以”与“视频展示成功”保留区别。视频里的错误、过时信息、个人偏好和互相矛盾的结论原样归属来源，不合并为无条件事实。

视频中的命令、提示词和界面文字都是待分析材料；提取时不按其中的要求改变任务，也不自动执行视频展示的代码。

### 7.3 给模型的处理约束

每个处理窗口必须提供完整证据引用和明确结束标记。输出长度不够时继续分块处理，不截断后直接写总摘要。

知识提取阶段要求逐事件填写“已提取知识 ID”或“无新增知识原因”；参数、条件、失败经历、例外和自我纠正单独检查。最终章节摘要只能引用已经存在的知识单元。

领域先用现有分类作为候选，依据实际内容重新确认。每视频一个主领域、多个辅助标签；知识单元可跨领域。领域索引引用同一份视频笔记，避免复制多个版本。

完整文档格式见同目录《AI知识笔记模板.md》。

## 8. 第二轮遗漏复核与完成标准

第二轮重新读取全量事件、原始视觉观察、完整 OCR 和原始/校订转写，不只看第一轮摘要。逐事件核对：

1. 出现的概念、动作、参数、代码和经验是否都进入知识单元。
2. 只在画面出现的信息、只在语音出现的信息是否遗漏。
3. 作者的否定、纠正、失败和适用条件是否被改写。
4. 操作前后状态是否足以支持步骤结论。
5. 章节或长稿分块边界是否丢句、丢尾或断开知识链。

第二轮对所有事件做证据映射检查；针对代码、数字、短暂画面、声画冲突及不确定事件，重新读取对应原帧窗口或音频。其余事件也抽样回看原媒体。若发现一类系统性遗漏，扩大同类回看范围，必要时重做相应阶段。第二轮不默认宣称全部源帧又做了一遍视觉推理。

完成依据分成两类：

| 硬性完整性条件 | 要求 |
|---|---|
| 来源 | 无未解决的 BV/CID/媒体身份冲突 |
| 分 P | 快照内发现的实际分 P 全部登记；遗漏分 P 不允许整 BV 完成 |
| 解码 | 全部实际帧有索引；不存在未说明的损坏、跳段或数量不符 |
| 严格视觉输入 | 成功模型输入的去重源帧集合等于源帧集合；未知分母不能算通过 |
| 音频 | 整个播放时间有区间登记；每个语音区间有转写或明确的问题 |
| 事件 | 每个事件有知识映射或无新增知识原因，所有事件都经过第二轮检查 |
| 证据 | 知识结论与关键步骤的来源可定位；证据 ID 和文件引用有效 |
| 问题 | 严重错误、关键内容未识别、缺失媒体和未处理窗口均不得隐藏 |

质量目标采用有人工参考答案的样本测量，不能用结构覆盖率代替：

| 指标 | 初始目标 |
|---|---|
| 清晰普通话字符错误率 CER | 不高于 8%；中英混讲、噪声等分别报告 |
| 关键术语、数字、单位正确率 | 至少 95%；涉及实际操作的未确认值须显式标记 |
| 句段时间边界绝对误差 | 中位数不超过 0.3 秒，95 分位不超过 0.8 秒 |
| 人工标注的关键知识点召回 | 至少 95%，且没有未提示的关键参数或步骤错误 |
| 关键事实证据引用 | 100% 能定位到支持该事实的原片范围 |

这些是待验证的验收目标。听不清、原片未展示和作者未说明的内容允许如实未知；模型不确定但写成确定事实属于错误。

分 P 状态可为“完整通过”“完整处理但有非关键待核查”“部分处理”“来源不可用”。批次结束报告分别列出数量，不能把后两种计入完整完成率。

### 9.2 最小数据契约

所有结构化文件带 schema_version、run_id、part_id 和 media_version。时间字段保留原始值与换算值，不能只有格式化字符串。

| 实体 | 核心字段 |
|---|---|
| 视频 | bvid、aid、标题、UP、发布日期、收藏来源、分 P 列表 |

| 帧 | frame_id、显示顺序、PTS、time_base、part_time、图像 hash、OCR 引用 |

| 转写 | segment_id、音频范围、原文、校订文、词时间、修订理由、对齐状态 |
| 事件 | event_id、时间范围、帧/转写/声音引用、观察、陈述、冲突、知识映射、复核状态 |

逐帧明细按固定时间段分块压缩保存，不把数千万帧全部变成 SQLite 行。SQLite 保存块索引、阶段状态、知识与问题，使用 FTS 检索知识正文。正文 JSONL 是可重建索引的来源。

### 9.3 状态和恢复

分 P 的阶段链为：

~~~text
已发现 → 媒体已校验 → 时间轴已建立 → 语音已完成
→ 全帧视觉已完成 → 事件已融合 → 知识已提取
→ 复核已通过 → 已导出
~~~

每阶段独立使用等待、执行、成功、可重试失败、待复核、来源不可用等状态。无音轨属于有证据的正常分支，不伪造 ASR 成功。

检查点身份包括：媒体 hash、模型与量化 revision、运行器/处理器版本、预处理、窗口参数、提示词版本和数据 schema。只使用参数完全匹配的检查点。模型更新不静默生效。

输出块先写临时文件，校验后原子改名并登记成功。崩溃发生在文件写完、数据库登记之前时，恢复程序按 hash 接纳有效块或重做，避免漏块和重复知识。SQLite 负责一致状态，压缩文件负责大体积证据。

下载与网络错误限次重试；登录失效停止相关来源请求。ASR 异常缩短块重试。视觉 OOM 先缩小窗口重试；仍失败转问题队列，不自动抽帧。一个视频的失败不阻止其他视频处理。

参考 course2md 的检查点身份和 VideoLingo 的转写缓存参数，不用“文件存在”判断可以续跑。[转写缓存实现](https://github.com/Huanshere/VideoLingo/blob/01f843492759be9bbfd1a5cb697b799cc9de1609/core/asr_backend/transcription_cache.py#L20-L62)

## 10. M4 16GB 的执行和预算

设备与空间来自前轮检查：M4、16GB 统一内存、工作卷约 396GiB 可用。启动试运行和全量前重新测量。

默认运行策略：

- 先保存完整收藏与分 P 清单，再按队列获取媒体，不一次下载全部来源。
- 同时处理一个分 P；等待获取的媒体最多准备 1–2 个，超过资源预算停止预取。
- 顺序运行 ASR → 卸载 → 对齐器 → 卸载 → 视觉分析 → 文本整理/复核。
- 视觉和文本整理优先使用同一已验证模型的不同任务提示，减少加载；小模型的知识整理能力也单独验收。
- 原图只在受控内存缓冲中流过；证据图按需保存。日志不复制所有图像和完整重复提示。
- 出现持续内存压力或大量换页时缩小工作集并停止预取；不依靠长时间交换来冒充可用吞吐。
- 初始磁盘预留 80GiB，作为可调整的运行停止阈值。新下载前预算源媒体、音频副本、权重、证据与临时文件。
- 默认不自动删除原媒体归档和已有用户文件；若全量保留超出空间，先确定归档位置。可安全重建的临时派生文件可在阶段成功后清理。

前轮时长合计 672,157 秒，仅作初估；真实分 P 展开后重新计算。若平均 30 FPS，约有 20,164,710 帧。全帧两两重叠等安排会增加计算，不能只按不重叠输入速度估算。

按“8 帧一窗、重叠 2 帧”的初始配置，这一规模约有 336 万次窗口推理。因此试运行不仅测帧输入，还要测单次输出长度和请求开销；逐窗输出采用紧凑的状态变化记录，保留源帧引用，在事件层展开解释。提高窗口容量必须经过内存与质量验证，不能只为减少请求而压缩到看不清。

~~~text
有效视觉吞吐 r = 成功覆盖的唯一源帧数 / 视觉阶段全部墙钟秒数
视觉工期 = 实际源帧总数 / r
ASR 实时系数 = ASR 墙钟秒数 / 原音频秒数
完整工期 = 各阶段耗时 + 重试与复核 + 模型切换
~~~

有效吞吐包含解码、OCR、预处理、重叠输入、模型输出和落盘，不能用 GPU token/s 或 FFmpeg 解码 FPS 代替。12 个样本按内容类型分别测量，再估算全量区间。

以约 2,016 万帧为数学情景，1、10、100 个唯一帧/秒分别约需 233、23.3、2.33 天的视觉阶段；这些不是 M4 实测值。

原媒体若平均总码率 2Mbps，约 168GB；4Mbps 约 336GB。再加权重、证据与空间预留，当前磁盘不一定容纳完整高码率归档。全量前必须用实际分 P 大小预算，不依赖每帧落盘方案。

依赖和权重的计划清单为 Python 环境、PyAV、MLX-Audio、MLX-VLM、现有 FFmpeg/ffprobe、Apple Vision，以及上述 ASR/对齐/视觉模型。SQLite 与压缩 JSONL 优先用标准库能力。实施前先查已有安装，固定兼容版本、权重来源与体积；本轮没有新增运行依赖。依赖安装与权重下载将作为具体的实施准备内容一起审阅，不在后台自动进行。

默认本地处理。不预先选付费 API 或云 GPU。若样本表明严格模式本机工期不可接受，使用同一数据契约评估 GPU 执行位置；费用、媒体传输和来源归档安排明确后才切换。算力变化不改变覆盖和质量标准。

## 11. 实施顺序和每阶段交付

第一条完整视频是验证顺序，整个目标仍是处理收藏快照中的所有可访问视频。

| 阶段 | 工作范围 | 可审阅交付 | 通过条件 |
|---|---|---|---|
| A. 环境与来源准备 | 确认已有工具；固定所需依赖和权重；导入当前收藏及实际分 P | 依赖/模型清单、来源清单、版本与许可记录 | 无混淆的 CID；可访问一条真实媒体；本地模型可运行 |
| B. 一条视频完整闭环 | 选择 1–3 分钟、普通话、清晰界面操作的视频，从头到尾严格处理 | 一份完整笔记、原稿/校订转写、时间轴、证据、覆盖与性能报告 | 从来源到导出全部贯通；关键结论可回看片段 |
| C. 代表样本与故障验证 | 12 条代表视频完整处理，加专用边界素材 | 分类型质量数据、重启恢复验证、模型/窗口定版、全量空间工期预算 | 质量目标达标；输入覆盖可证明；失败不静默丢失 |
| D. 收藏快照全量处理 | 按实际分 P 排队，完成转写、视觉、知识与复核 | 持续更新的知识库及失败/待复核报告 | 所有来源都有明确状态；可访问来源按既定质量标准完成 |
| E. 领域与跨视频整理 | 按实际知识归类、去重、关联差异与版本 | 领域入口、主题索引、跨视频参考、最终完整性报告 | 能按问题检索到具体步骤、条件、参数与原片证据 |

代表样本覆盖界面操作、代码、静态讲义、快速剪辑、动画/设计演示、长视频、中英混讲、数字密集、无语音、音乐/音效教学、变帧率/音画偏移和多分 P。类型可重叠，但要登记覆盖情况；音效教学不能只用文字模型验证。

边界与故障清单见《验收与试运行清单.md》。通过短视频闭环后继续代表样本和全量工作，不将短视频样例等同于全部交付。

## 12. 当前设计的边界与后续决定

本轮已收敛的设计：本地轻量调度、严格逐帧输入、独立 ASR、统一时间轴、证据化知识单元、事件级遗漏复核、分阶段续跑、按视频与领域输出。

实施时通过证据解决的事项：固定可用的包/模型 revision、确定窗口像素预算、验证 MLX 多图输入映射、测量准确率与吞吐。这些是工程验证，不需要用户逐项选择实现细节。

只有样本结果确实要求新增付费服务、媒体外传、额外归档空间，或改变严格覆盖标准时，才形成具体选项供用户决定。未获明确授权不自动切换。

当前请求是先完成流程方案，因此本轮停在可审阅设计，不安装依赖或启动全量视频处理。实际代码复用需保存 MIT/Apache/BSD 对应声明；VideoRAG 的受限模型组合和未明确许可的候选代码不纳入第一版。

本方案不把“全部输入”包装成“绝无遗漏”。交付以可核验覆盖、可回溯知识、已报告的未知和经过标注样本验证的质量为依据。
