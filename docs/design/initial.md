# 视频全帧学习、时间轴转写与知识库建设方案

版本：v1.0  
日期：2026-10-26  
状态：设计方案；本轮未安装依赖、下载模型或启动全量视频处理。

## 1. 决策摘要

建议建设一套本地优先、可接 GPU 推理节点的视频学习流水线：

**浏览器导入收藏 → 获取并校验实际媒体 → 全帧视觉处理与独立语音转写 → 声画时间轴对齐 → 逐段知识提炼 → 遗漏检查 → 按视频生成 Markdown 并按领域索引。**

本次需求按“严格逐帧模式”设计：所有原始解码帧都进入视觉语义模型的输入范围，有逐帧登记和模型输入回执；语音从该视频自己的音轨生成，知识结论带原视频时间段和证据引用。

系统同时保留一种可选的加速模式：全帧进行画面变化/OCR 扫描，再按事件选择画面做语义分析。它适合降低成本，但不等同于每帧都进入视觉模型，不能用它冒充严格模式完成。

“把全部知识记录下来”的工程目标是：每段内容都有处理记录、每条结论都有证据、未识别和有歧义的部分都有待复核项。模型输入覆盖率达到 100% 仍不代表理解准确率达到 100%，因此需要第二轮遗漏检查与有针对性的人工抽检。

## 2. 当前已确认的条件

| 项目 | 现状 | 对方案的影响 |
|---|---|---|
| 设备 | Mac mini、Apple M4、16GB 统一内存 | 本机同时只运行一个主要推理模型；控制视觉窗口与上下文大小 |
| 工作磁盘 | 剩余约 396GiB | 不把数千万帧全部保存成图片；需要磁盘预算与停止阈值 |
| 收藏清单 | 750 条收藏，739 个不同 BV 条目 | 清单可复用；以 BV 和实际 CID 重新绑定媒体 |
| 时长 | 收藏接口汇总约 186 小时 42 分钟 | 作为初步规模估算，展开全部分 P 后重新核算 |
| 多分 P | 已有数据中 20 个条目的 page 字段大于 1 | 不把这个字段直接解释为“应观看的分 P”；重新读取实际分 P 列表 |
| 现有产物 | 739 份基于标题、简介、封面的预整理笔记 | 保留为清单资料；第二版从实际声画内容重建 |
| 原字幕记录 | 520 条记录可读，但抽查出现主题不匹配 | 先调查来源绑定和缓存；字幕仅作对照，主转写来自原音频 |

对旧字幕记录的附加检查发现，520 个字幕 URL 路径中有 368 个没有呈现预期的 aid/cid 组合。URL 命名本身不能证明字幕属于另一视频，但这暴露了旧流程缺少“返回媒体身份校验”的问题。不能据此直接断言 B 站字幕服务普遍不可靠。

当前目录没有现成的应用工程；可复用的是收藏清单、封面 OCR 经验和目录结构，需新建轻量处理工程。

## 3. 可选方案与推荐

| 方案 | 能做到什么 | 代价与限制 | 选择 |
|---|---|---|---|
| 浏览器播放、截图、读取页面字幕 | 人工式查看片段，处理少量视频 | 无法可靠证明原始帧全部覆盖；浏览器截图没有完整原始音视频时间轴 | 用于导入、权限访问和复核 |
| 全部本地处理 | 独立转写、原始帧处理、证据保存、离线运行 | M4 16GB 的严格逐帧视觉语义处理可能非常慢 | 作为基础路径和首轮样本验证 |
| 本地调度＋可替换 GPU 推理节点 | 保持同一处理标准，将视觉重任务交给更强算力 | 涉及额外算力、费用和媒体传输，需要实施时作出明确决定 | 推荐的总体架构 |

采用同一套媒体、时间轴、任务状态和知识数据格式。GPU 节点只替换推理执行位置，不改变逐帧要求和验收标准。先在本机测量实际吞吐，再决定全量计算位置。

## 4. 总体架构

~~~mermaid
flowchart TD
    A[B站收藏清单或本地视频] --> B[媒体获取与身份校验]
    B --> C[原始时间轴与分P清单]
    C --> D[全帧解码、OCR、视觉语义]
    C --> E[音频提取、语音转写、强制对齐]
    C --> F[非语音声音事件]
    D --> G[统一声画事件时间轴]
    E --> G
    F --> G
    G --> H[逐段知识与经验记录]
    H --> I[证据检查与遗漏复核]
    I --> J[逐视频Markdown和领域索引]
    I --> K[未解决问题与重试队列]
~~~

基本技术组合：

- Python：任务调度、时间轴融合、结构化数据、Markdown 导出。
- FFmpeg / ffprobe：媒体解析、音轨提取、逐帧解码和原始时间戳。
- SQLite：视频、分 P、任务状态、知识单元、错误和索引。
- 每视频压缩 JSONL：逐帧账本、模型输入记录、语音片段与事件。
- Swift / Apple Vision：原始画面文字识别，复用当前电脑已经验证过的本地 OCR 能力。
- ASR 和视觉模型通过固定接口接入，避免调度代码依赖某个模型的私有输出格式。

第一版使用单机任务队列和独立工作进程即可。暂不引入 Redis、Celery、Kubernetes 或独立向量数据库；文本检索先使用 SQLite FTS。

## 5. 媒体获取与来源绑定

### 5.1 收藏条目与分 P

以 BV 条目建立视频记录，再展开该视频的实际分 P 列表。每个分 P 使用独立 CID、标题、时长和媒体记录。

去重分两级：

1. 相同 BV 的重复收藏合并来源收藏夹。
2. 相同 BV 下的不同 CID 分别处理；不因为 BV 相同而跳过其他分 P。

先前收藏接口中的 page 字段不作为分 P 选择的依据。739 是当前 BV 条目数，不是最终媒体分段数。

### 5.2 获取实际媒体

浏览器负责登录态、收藏导入和访问权限。处理器获取当前账号可正常访问的媒体文件，或者接受本地导出的视频。获取不到完整媒体时，条目进入“来源不可用”队列，并保留原因。

每次获取保存：

- BV、aid、CID、分 P 序号与标题。
- 来源地址、获取时间、原视频发布日期。
- 媒体时长、画面尺寸、视频和音频流编号、音轨语言。
- 原文件 SHA-256、音频指纹、文件大小。
- 实际返回的媒体身份及其与清单的比对结果。

禁止只把“请求参数里的 CID”抄进结果当成已校验身份。返回身份、时长、内容片段需要相互吻合。临时媒体 URL 过期时重新解析；登录凭据不进入笔记、日志或 GPU 任务。

## 6. 严格逐帧观看的实现标准

### 6.1 逐帧解码与原始时间轴

顺序解码全部原始视频帧。每帧记录：

- 分 P 标识、帧编号。
- 原始显示时间戳 PTS 和时间基准。
- 归一化后的秒数或毫秒数。
- 图像校验值、尺寸、处理状态。
- OCR 结果引用、视觉模型输入批次和返回记录。

变帧率视频以实际 PTS 为准，不能用“帧编号 ÷ 名义帧率”计算时间。音轨起始偏移、容器起始时间和分块偏移也要统一映射。

ffprobe 能列出逐帧信息、统计帧数；官方文档也提醒区间 seek 的实际起点可能与请求位置不同，因此分块结果必须按实际时间戳回填，而不能假定 seek 精确命中。[FFmpeg 官方 ffprobe 文档源码](https://github.com/FFmpeg/FFmpeg/blob/master/doc/ffprobe.texi)

### 6.2 视觉文字和画面语义分别处理

每帧至少产生两个方面的记录：

1. **画面文字：** 界面标签、代码、命令、数值、公式、参数和讲义内容，保留文字位置与识别置信度。
2. **视觉语义：** 当前对象和状态、界面变化、演示动作、前后对照、操作结果、动画或场景变化。

代码、公式和小字区域在原始分辨率上裁剪识别。原始 OCR 和修订文本分开保存；模糊或遮挡的字符标为不确定，不补写不存在的代码。

Apple Vision 支持本地多语言 OCR，提供快速和准确两种识别路径。中文的语言纠错和自定义词表有专门限制，因此术语修订放在保留原始 OCR 之后进行。[Apple 官方文字识别说明](https://developer.apple.com/documentation/vision/recognizing-text-in-images)

### 6.3 连续帧窗口

视觉模型按连续帧小窗口处理，窗口长度由显存、分辨率和输入 token 预算决定，不能固定把长视频一次提交。

- 每个窗口显式附带每帧的编号与时间。
- 本机试验从每窗 8–16 帧、相邻窗重叠 2–4 帧开始；这是待测的初始配置，最终由实际像素与上下文预算确定。跨多个窗口的动作通过事件状态继续跟踪。
- 相邻窗口保留少量重叠帧，跨窗口保留动作和主题状态。
- 窗口可一次包含多帧，但每个输入帧都必须在回执中有对应记录。
- 在 16GB 内存上，从小窗口开始测量；OOM 时减小窗口或裁剪区域，不暗中降低输入帧率。
- 单帧记录帮助保住短暂文字；连续帧记录用于判断动作、转场和前后关系。

画面中鼠标移到按钮上不等于已经点击。点击、键盘输入和隐藏操作只有在画面、声音或作者讲解有依据时才能确定，否则记录为推断或未展示。

### 6.4 防止模型预处理暗中抽帧

Qwen3-VL 官方使用说明中，视频输入默认采样帧率是 2 FPS；相关服务接口也存在默认采样开关。因此直接上传一段视频并要求“逐帧看完”不能证明逐帧覆盖。[Qwen3-VL 官方视频处理说明](https://github.com/QwenLM/Qwen3-VL#usage)

严格模式需要检查：

- 解码帧总数。
- 每个推理请求提交的源帧 ID 列表。
- 处理器实际保留的帧 ID 和帧数。
- 输入限制是否截断后半段、降低帧数或重复缩放。
- 所有分 P 的帧区间是否形成完整覆盖。

不支持查看或控制实际帧输入的模型服务，不用于“严格逐帧已完成”的证明。

| 能力 | 严格逐帧模式 | 可选加速模式 |
|---|---|---|
| 全部原始帧解码登记 | 是 | 是 |
| 全部帧进入视觉语义输入 | 是 | 否；事件或变化区域采样 |
| 原始时间轴 | 保留 | 保留 |
| 输出每段内容的来源 | 是 | 是 |
| 可标记严格逐帧完成 | 可以，且需通过审计 | 不可以 |

## 7. 带时间轴的语音转写

### 7.1 从原音频独立转写

保留原音轨，另生成适合 ASR 的推理副本。模型需要重采样时记录转换；不能改变原片播放速度或把静音删除后重新排列时间。

处理顺序：

1. 识别有声、语音、音乐、静音等区间。
2. 对语音区间进行离线转写，保留完整时间偏移。
3. 在合理语句边界切块，相邻块少量重叠，按文字和时间共同去重。
4. 使用原语音与转写文本做强制对齐，细化到词级或中文字符级时间。
5. 结合 OCR 和领域词表提出术语、代码和数字的修订候选。
6. 保存原始转写、校订稿、修订理由及对应音频范围。

语音活动检测只用于安排任务，不把被判为静音或音乐的音频永久丢弃。整条音轨要有连续区间账本，低音量、音乐覆盖、边界区间另行复核，避免“检测器没找到语音”被当成“音频没有内容”。

B 站字幕可以作为辅助对照。只有在来源身份、持续时间和内容对应关系通过校验后，才参与纠错；不能覆盖独立 ASR 原稿。

### 7.2 ASR 选型

本机基线采用 whisper.cpp：有 Apple Silicon、Metal 与 Core ML 的明确支持，可先完成带句段时间戳的独立转写。它的词级时间戳在项目文档中标注为实验性，不能直接把该输出当作精确词级对齐的验收结果。[whisper.cpp 官方项目](https://github.com/ggml-org/whisper.cpp)

精确对齐候选采用 Qwen3-ForcedAligner；中文复杂音频可同时评估 Qwen3-ASR。官方对齐模型支持中文、英文等语言，并可输出词或字符时间戳；单次对齐语音上限为 5 分钟，因此调度器采用更短块并回填到原片时间轴。先验证实际运行后端、中文专业词和数字表现。[Qwen3-ASR / ForcedAligner 官方说明](https://github.com/QwenLM/Qwen3-ASR#forcedaligner-usage)

WhisperX 可作为独立对齐替代方案。它采用语音活动检测和强制对齐，但对数字、重叠说话和说话人区分有已知限制，仍需样本验证。[WhisperX 官方限制说明](https://github.com/m-bain/whisperX#limitations-)

### 7.3 转写产物

每个分 P 输出：

- 原始 ASR 结构化稿：文本、开始/结束时间、识别状态。
- 校订后的带时间轴 Markdown。
- SRT / VTT，方便播放器联动。
- 词或字符级时间戳 JSONL。
- 听不清、术语冲突、数字冲突和多人重叠说话清单。

默认区分说话人编号，不推断真实身份。单人教程不必加载额外说话人模型。

### 7.4 不属于语音的声音

音色、节奏、音效、发音示范或设备噪声本身也可能是教学内容。它们另存为带时间的声音事件，保留可回放证据，不能用空白 ASR 结果判断“这里没有知识”。

没有语音的视频仍进入完整视觉处理。没有可识别内容的区间标明原因。

## 8. 统一声画事件时间轴

所有数据以同一分 P 的原始时间轴对齐。

事件划分综合：讲解主题变化、画面切换、文字/代码变化、演示动作、声音变化。每个事件保存：

- 时间范围、参与帧范围与语音片段。
- 画面里出现了什么，作者说了什么。
- 是否形成动作前后关系。
- 有没有只在画面出现、未被说出的信息。
- 有没有只在音频出现、画面没有展示的信息。
- 声画矛盾、看不清或理解不确定的部分。

静态讲义上长时间讲解的内容也完整覆盖；快速操作的关键状态不会因为没有说话而被忽略。事件摘要用于组织资料，不替代逐帧记录。

## 9. 从视频中提炼知识和经验

### 9.1 先记录知识单元，再生成总摘要

对每一个事件提取以下内容：

| 知识类型 | 必需字段 |
|---|---|
| 概念和原理 | 定义、为什么、适用前提、例子、反例或限制 |
| 操作技术 | 目标、环境/版本、输入、步骤、参数、输出、验证方法 |
| 经验和取舍 | 情境、尝试、失败、调整、结果、适用范围 |
| 工具或产品判断 | 测试条件、评价依据、时间点、作者立场、局限 |
| 演示或作品参考 | 可观察效果、构成要素、呈现顺序、已展示与未展示的实现信息 |

代码、命令、公式、尺寸和参数作为结构化内容保留；不能只在总摘要里写“介绍了一个技巧”。

### 9.2 每条知识绑定证据

每个知识单元记录：

- 知识 ID、主题、领域和检索标签。
- 一句结论与完整解释。
- 前置条件、操作步骤、参数和常见失败。
- 原片时间段、证据帧 ID、转写片段 ID。
- 信息性质：作者陈述 / 画面演示 / 系统推断 / 另行验证。
- 不确定点及冲突。
- 审核状态。

置信度依据证据是否清晰、声画是否一致及复核结果产生，不把模型自行给出的百分比当作准确率。

示意结构，下面不是从某视频抽出的实际知识：

~~~yaml
knowledge_id: P001-K007
topic: 某项具体操作
source_span: 00:01:23.400–00:02:10.800
evidence_frames: [F002502, F002520, F002580]
evidence_transcript: [S0031, S0032]
basis: observed_demo
prerequisites: [软件版本、已有状态]
steps: [可观察的步骤]
parameters: [已在原片确认的值]
validation: 可观察的成功结果
limits: [未展示或不确定的部分]
~~~

### 9.3 逐视频 Markdown 的内容

主文件应包含：

1. 视频来源、发布日期、软件或设备版本、分 P 列表。
2. 这条视频能解决的问题与学习前提。
3. 章节与带时间轴的内容导航。
4. 完整知识单元，按原理、技术、步骤、参数、经验、失败情形整理。
5. 代码、公式、参数表和必要证据图。
6. 适用边界、作者观点与未验证结论。
7. 可供 AI 检索的问答入口和关键词。
8. 完整转写、事件时间轴与覆盖报告的链接。

主文件是阅读入口；详细知识单元和完整转写单独保留，避免把大量内容压缩成一页摘要后丢失细节。

领域分类根据实际内容重新生成，允许一个主领域和多个标签。旧版基于元数据的分类作为候选，不直接继承为已核验分类。

AI 使用时按问题检索这些知识单元，并回溯原片证据；后续有需要再导出训练样本。

任务数据库主要实体：视频、分 P、媒体文件、任务阶段、模型请求、语音片段、声画事件、知识单元、复核问题。

## 11. 怎样证明“处理完了”

一个视频的完成标准同时包含处理覆盖和知识质量。

| 检查项 | 建议验收标准 |
|---|---|
| 来源对应关系 | BV、CID、媒体时长和内容抽检对应；无未解决的身份冲突 |
| 分 P 范围 | 已发现的实际分 P 全部登记并处理 |
| 解码覆盖 | 全部原始帧都有账本记录；解码错误显式报告 |
| 严格语义覆盖 | 全部帧都有视觉模型输入记录和对应处理回执 |
| 语音区间覆盖 | 每个语音区间都有转写或“听不清”标记；不静默跳过 |
| 时间轴一致性 | 无错误负时间、跨分 P 混用、无说明的偏移和重复块 |
| 知识证据 | 每条知识结论都有源时间段和证据类型 |
| 内容段落覆盖 | 每个事件都映射到知识单元或“无新增知识”的原因 |
| 遗漏检查 | 第二轮直接检查原始声画事件，补找第一轮遗漏内容 |
| 完成状态 | 严重冲突未解决时保持待复核，不因 Markdown 已生成而标记完成 |

在已人工标注的样本上，提出以下初始质量目标，随后按真实素材校准：

- 清晰普通话样本的中文字符错误率目标不高于 8%。
- 关键术语、数字、单位单独检查，目标准确率至少 95%。
- 句段时间边界误差中位数不超过 0.3 秒、95 分位不超过 0.8 秒。
- 中文字符或词级对齐若不能达到相应目标，保留句段时间，不伪造更精确的时间。
- 所有实现步骤、代码和参数都有可回溯证据；重要缺项进入复核队列。

这些是待验证目标，不是对任意噪声、方言或重叠讲话的保证。

专门准备能暴露处理错误的样本：只闪现一帧的命令、变帧率视频、音画起点不同的视频、跨块说话、连续滚动的代码、无语音教程、多分 P、重复字幕、长时间音乐与多人重叠说话。

## 12. 模型与依赖选择

| 组件 | 推荐用途 | 选用依据与需要验证的部分 |
|---|---|---|
| FFmpeg / ffprobe | 原媒体解析、逐帧时间轴、音轨提取 | 已有本地工具；发布打包时核对所用构建的许可 |
| Apple Vision | 本机中文/英文画面 OCR | 系统能力，已在本机做过封面 OCR；原片小字和代码仍需样本测试 |
| whisper.cpp | M4 上的 ASR 基线 | MIT；Apple Silicon 路线明确；词级时间戳不直接视为精确对齐 |
| Qwen3-ASR + ForcedAligner | 中文转写及词/字符级对齐候选 | 官方提供离线识别和对齐；运行后端、内存、专业词表现需实测 |
| Qwen3-VL-4B-Instruct | 本地小模型视觉候选 | 官方模型卡为 Apache-2.0；量化后仍需测量峰值内存、短暂文字与多图时序表现 |
| MLX-VLM | M4 本地视觉推理运行器候选 | MIT，提供 Mac/MLX 和多图接口；必须验证具体模型组合和全部帧输入，不假定视频入口支持所有模型 |
| 较强的视觉模型/GPU 节点 | 全量严格逐帧和困难片段复核 | 保持同一输入账本与输出格式；费用和媒体传输在实施时单独决定 |

Qwen3-VL-4B 官方模型卡、MLX-VLM 项目分别提供模型和本地运行能力依据，但这不等于已在本机验证该组合满足严格逐帧要求。[Qwen3-VL-4B 模型卡](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct)、[MLX-VLM 项目](https://github.com/Blaizzy/mlx-vlm)

Qwen3-ASR 的官方模型卡标明 Apache-2.0；具体依赖和权重固定到已验证版本与 revision，保存运行环境清单，不把主分支更新当作自动升级。[Qwen3-ASR 模型卡](https://huggingface.co/Qwen/Qwen3-ASR-1.7B)

不以文档里的服务器吞吐或宣传基准推算你的 M4 性能。不同音视频类型分别测量。

## 13. 时间、存储与算力预算

### 13.1 帧数量

以当前初估时长 672,157 秒计算：

- 平均 30 FPS：约 20,164,710 帧。
- 平均 60 FPS：约 40,329,420 帧。

实际数量从各媒体解码统计取得。每秒抽一帧只有约 67 万帧，与严格逐帧不是同一工作量。

### 13.2 处理耗时

视频时长不等于计算耗时，计算速度可能快于或慢于播放速度。

严格视觉耗时约为：总帧数 ÷ 实测端到端每秒处理帧数。以下仅为 30 FPS 规模下的数学情景，不是本机性能承诺：

| 实测等效吞吐 | 仅视觉阶段约需 |
|---:|---:|
| 1 帧/秒 | 233 天 |
| 10 帧/秒 | 23.3 天 |
| 100 帧/秒 | 2.33 天 |

这里的等效吞吐必须包含图像预处理、模型编码、输出、重试和结果保存，不能只用解码速度或生成 token 速度替代。

ASR 使用实时系数估计：处理时间 ÷ 音频时长。若样本测得实时系数 0.25，186.7 小时音频的 ASR 阶段约需 46.7 小时；这同样只是情景计算。完整耗时还包含声画对齐、知识提炼和复核。

### 13.3 存储

- 原媒体若平均总码率 2 Mbps，约占 168GB；4 Mbps 则约 336GB。实际以下载清单核算。
- 16kHz、单声道、16 位 PCM 音频约占 21.5GB；这是推理副本估算，原始音轨另行保留。
- 约 2,016 万帧若每张图片 100KB，将超过 2TB，因此不采用“全部帧落盘成图片”的方式。
- 用流式解码和内存环形缓冲处理帧；保留原媒体、压缩账本和必要证据图。
- 模型权重、缓存和证据图另外计入预算。设磁盘最低空余阈值；达到阈值后暂停，不自动降低画质、跳帧或删除用户原文件。
- 原媒体保存或转存位置在全量前按实际体积确定；已有用户文件不进入自动清理范围。

### 13.4 云端或 GPU 费用

先完成样本，再按实际数据估算：

- 计算费＝GPU 小时数 × 供应方单价。
- API 费＝实际图像/视觉 token、文本输入输出、重试 × 对应单价。
- 加上存储与传输费用。

本方案不预设付费服务、账号或固定金额。没有实际样本吞吐与模型输入量时，不给出看似精确的全量预算。

## 14. 批处理与断点续跑

任务状态建议为：

**已发现 → 媒体已校验 → 语音已转写 → 全帧已处理 → 声画已对齐 → 知识已提炼 → 复核已通过 → 已导出。**

设计要求：

- 任务以分 P 和处理阶段为单位保存检查点。
- 每阶段记录输入文件 hash、模型/提示词版本和参数。
- 崩溃后只重做未完成或依赖已改变的阶段。
- 单个视频失败不阻塞其他视频；错误有分类、限次重试和可见原因。
- 输出使用临时文件后原子提交，避免半份笔记被识别为成功。
- 模型切换只使相关阶段失效，不重新抓取所有媒体。
- 本机重模型串行运行；轻量解码、文件校验和索引按测得的内存余量安排。
- 连续运行展示已完成/失败/待复核视频数、完整帧数、语音覆盖、剩余时间估计和空间。
- 完成标记由覆盖检查产生，不能由文件数量产生。

## 15. 实施顺序与完成条件

### 阶段一：一个短视频的完整闭环

选择一条 1–3 分钟、画面包含明确操作与讲解的视频，完整处理实际媒体。

交付：

- 已校验媒体身份与原始时间轴。
- 全部帧登记、全部帧语义输入证明。
- 带时间轴转写、词/字符对齐结果。
- 事件时间轴、知识单元和一份可回溯 Markdown。
- 缺项与实测耗时报告。

完成条件：能从笔记里的任意结论回到对应画面和音频；短暂一帧信息不会被处理器抽掉。

### 阶段二：12 类代表素材验证

候选包括：Godot 短教程、Blender 小字界面、UI 动效、AI 工具中英混讲、代码滚动、长课、多人对话、噪声口音、无语音演示、音乐/音效教学、变帧率、多个分 P。

先用代表片段定位质量问题，再完整处理代表视频。记录每种素材的 ASR 错误、时间误差、逐帧遗漏、内存峰值、帧吞吐和单视频成本。

完成条件：确定模型组合、窗口预算、质量门槛和全量算力/存储预算。

### 阶段三：全量内容处理

重新展开 739 个 BV 条目的实际分 P，启动可续跑队列。逐条处理实际声画，生成知识库第二版。

完成条件：全部可访问来源都有明确完成或失败记录；没有“只因写了标题简介就算处理完成”的条目。

### 阶段四：知识库质量与领域整理

直接从声画事件执行第二轮遗漏检查，修正知识单元、代码和参数，重新进行领域分类与跨视频去重关联。

完成条件：全部视频都有主笔记、转写和覆盖报告；严重冲突已解决或清楚列出，领域索引可以实际检索到具体技术和经验。

先完成小闭环是实施顺序，后续继续覆盖本次全部要求，不把样本成果当作全量完成。

## 16. 风险、兼容与回退

- **媒体身份或分 P 绑定错误：** 先修正媒体清单，相关下游结果全部失效重做。
- **模型抽帧或截断：** 请求帧清单与处理器输出计数不一致时失败，调整窗口后重试。
- **ASR 虚构、专业词或数字错误：** 对照原音频与 OCR，保留原稿和修订记录，关键内容复核。
- **画面未显示的操作：** 记录未展示，不根据结果填补隐藏步骤。
- **视频中的错误或过时观点：** 保留作者立场、日期与版本，不把转述改写成已证实事实。
- **本机性能不足：** 先缩小并发与窗口；严格模式不能自动降为抽样模式。
- **磁盘不足：** 停止新增媒体，保留检查点，先确定转存方案。
- **数据格式变化：** 数据文件带 schema_version；升级前备份数据库，旧版预整理文件保留，v2 单独生成。
- **来源失效：** 保留不可用清单与可访问性原因，不能以元数据笔记冒充完整分析。

## 17. 建议采用的实施基线

1. 本地 Python＋SQLite 调度，FFmpeg 全帧解析，Apple Vision 处理原画面文字。
2. 从原视频音轨独立 ASR，先建立句段时间轴，再用经验证的强制对齐细化。
3. 严格模式显式提交全部帧；本机小模型先验证，重任务可切换 GPU 节点。
4. 知识按事件逐条提取，保存步骤、参数、经验、限制与时间戳证据。
5. 第二轮遗漏检查和覆盖报告通过后，才标记视频完成。
6. 旧的 739 份预整理保留；完成内容处理后另交付知识库 v2。

这是实施提案，不代表相关模型已经在本机验证，也不代表已开始全量处理。实施授权后先完成短视频闭环与代表样本测量；新增依赖、权重、付费算力和媒体外传等选择按确定的范围处理。
